# RimFacilityCompat 优化技术方案

## 0. 优化目标

保持当前“三态声明式注入、运行时即时生效、不落盘改 Def”语义不变，重点降低：

1. 启动扫描时间：当前最坏约 `O(K·q·N)`，主要来自未缓存的 `ResolveType`；
2. 启动注入时间：当前即使无配置也全量跑 `ApplyInjection`；
3. 单次 UI 改动延迟：当前每次单击都“全类别重建 + 全地图重连”；
4. 反向索引重建范围：当前会重建“旧∪新全部链接设施”，而不是只重建增删设施；
5. 配置窗口每帧 `ShouldLink` 的线性查找。

建议分阶段实施，每阶段可独立回归。

***

## 0.5 现状核对说明（2026-09-09 代码审计后补充）

本方案撰写时对数据模型的描述需按以下现状修正，其余假设与 `Source` 现实现一致：

- **不存在独立的** **`excludedTargets`** **黑名单字典**。Settings 只持久化 `linkedTargets`（Source/Data/Settings.cs），三态语义内嵌其中：**无 key = 未配置（回退 originalLinks）；有 key 且空列表 = 显式全断开；有 key 且非空 = 显式启用集合**。方案的"黑名单"操作（DisableAllTargets 等）写入的即是空列表态，无需新增字典。
- `originalLinks` / `categories` 不落盘，每次启动由 `FacilityPatcher.Apply()` 阶段一扫描重建。
- 所有"仅单个 key"的操作（如断开某条链接）都会**物化**出对应 key（从 originalLinks 拷贝），因此 `linkedTargets.Count == 0` 严格等价于"无任何用户显式配置"。
- UI 与注入现状：`ApplyInjection` 无范围参数、返回 int；`RelinkSpawnedThings()` 无参全地图遍历；任何改动经 `Dialog_FacilityMatrix.ApplyAndSave` 全量执行（对应 §4/§5 的优化动机成立）。

## 1. Phase 1：给 `ResolveType` 加“会话级字典缓存”

### 问题

`FacilityScanner.ResolveType()` 每次对每个已知类别都全量扫一遍 `DefDatabase<ThingDef>.AllDefs`，并且结果不缓存。

### 方案

在 `FacilityScanner` 内加缓存，并在每次 `ScanAll()` 开头清空。

```csharp
private static Dictionary<string, Type>? typeCache;

private static void ResetTypeCache()
{
    typeCache = null;
}

private static Type? ResolveType(string className)
{
    if (typeCache == null)
    {
        typeCache = new Dictionary<string, Type>();

        foreach (var def in DefDatabase<ThingDef>.AllDefs)
        {
            var type = def.thingClass;
            if (type != null && !typeCache.ContainsKey(type.Name))
                typeCache[type.Name] = type;
        }
    }

    return typeCache.TryGetValue(className, out var result) ? result : null;
}
```

在 `ScanAll()` 第一行调用：

```csharp
public static Dictionary<string, CategoryInfo> ScanAll()
{
    ResetTypeCache();
    // ... 原逻辑
}
```

### 效果

- 每次扫描只构建一次 `Type.Name → Type` 字典；
- `ResolveType` 从 `O(q·N)` 降到 `O(1)`；
- 玩家增删 Mod 后重启，`ScanAll()` 会清空并基于新 DefDatabase 重建，无过期问题。

## 2. Phase 2：优化启动扫描的其它显式瓶颈

### 2.1 普通 Building 连通分量改用邻接表 BFS

当前 `AddGenericBuildingGroups` 里每个目标都会 `remaining.Where(...)` 扫描剩余目标，最坏 `O(B²·d)`。

改为一次性建立“设施 defName → 目标”索引，再 BFS：

```csharp
var facilityToTargets = new Dictionary<string, List<ThingDef>>();

foreach (var target in genericTargets)
    foreach (var facility in targetLinks[target])
    {
        if (!facilityToTargets.TryGetValue(facility.defName, out var list))
            facilityToTargets[facility.defName] = list = new List<ThingDef>();
        list.Add(target);
    }

var remaining = new HashSet<ThingDef>(genericTargets);

while (remaining.Count > 0)
{
    var first = remaining.First();
    remaining.Remove(first);

    var componentTargets = new List<ThingDef> { first };
    var componentFacilities = new Dictionary<string, ThingDef>();
    var queue = new Queue<ThingDef>();
    queue.Enqueue(first);

    while (queue.Count > 0)
    {
        var target = queue.Dequeue();

        foreach (var facilityDef in targetLinks[target])
            componentFacilities[facilityDef.defName] = facilityDef;

        foreach (var facilityDef in targetLinks[target])
        {
            if (!facilityToTargets.TryGetValue(facilityDef.defName, out var candidates))
                continue;

            foreach (var candidate in candidates)
            {
                if (remaining.Remove(candidate))
                {
                    componentTargets.Add(candidate);
                    queue.Enqueue(candidate);
                }
            }
        }
    }

    // 生成 category，逻辑同原代码
}
```

复杂度从最坏 `O(B²·d)` 降到 `O(B·d + B)`。

### 2.2 `ScanOriginalLinks` 去重阶段不要用 `List.Contains`

当前对同一个 key 反复 `Contains`，最坏接近 `O(L²)`。

用临时 `HashSet` 构建，最后再转 `List`：

```csharp
public static Dictionary<string, List<string>> ScanOriginalLinks(...)
{
    var result = new Dictionary<string, List<string>>();

    // ...原有外层循环...

    // 用一个局部 HashSet 去重后一次性转 List
    foreach (var group in temp.GroupBy(...))
        result[key] = group.Select(x => x.defName).Distinct().ToList();

    return result;
}
```

更简单做法：

```csharp
if (!result.TryGetValue(key, out var set))
{
    set = new HashSet<string>();
    result[key] = new List<string>(); // 或最后统一转换
}
```

如果你后续把 `originalLinks` 类型改成 `Dictionary<string, HashSet<string>>`，这一步也可以彻底省掉 List。

## 3. Phase 3：启动时无配置则跳过全量 `ApplyInjection`

### 问题

当前启动阶段即使 `linkedTargets` 为空，也全量执行一次 `ApplyInjection`，遍历“所有类别 × 所有目标 × 所有设施”，只是为了确认“无需修改”。

### 方案

在 `FacilityPatcher.Apply()` 里判断：

```csharp
if (settings.linkedTargets.Count == 0)
{
    // 没有用户显式配置：ShouldLink 全部回退 originalLinks，
    // 当前 Defs 已经是 XML 原始状态，不需要重建。
    applied = 0;
}
else
{
    applied = ApplyInjection(settings).Applied;
}
```

注意：`linkedTargets.Count == 0` 包括“首次运行 ResetToOriginal 后”的干净状态，正好覆盖最常见的无配置启动路径。

### 实施要求

1. **只跳** **`ApplyInjection`，阶段一（ScanAll / ScanOriginalLinks / SnapshotOriginalComps）必须照常执行**：`targetsWithOriginalComp` 启动快照与 `originalLinks` 是后续一切注入/孤儿清理的基准，即使无配置也要在启动时重建（现 `Apply()` 阶段一无条件执行，保持不动）。
2. **跳过逻辑依赖“defs 恒为 XML 原始状态”前提**（由运行时注入不落盘保证）：在跳过分支注释中钉死此前提，并同步守卫“落盘改 Def / 进程内热重载 / 第三方改 def”等会破坏前提的扩展点。

### 效果

- 无配置时启动阶段省掉整个 `ApplyInjection`；
- 有配置时才全量重建，保留三态语义。

## 4. Phase 4：`ApplyInjection` 改为“可限定类别/目标”并返回变更集合

### 问题

现在一次单击也会遍历所有类别，且 `RelinkSpawnedThings()` 无法知道哪些目标变了，只能全图扫。

### 4.1 引入返回结构

```csharp
public sealed class InjectionResult
{
    public int Applied;
    public List<ThingDef> ChangedTargets = new();
}
```

### 4.2 添加可选范围参数

```csharp
public static InjectionResult ApplyInjection(
    FacilityCompatSettings settings,
    string? onlyCategory = null,
    string? onlyTargetDefName = null)
{
    var result = new InjectionResult();
    var affectedFacilities = new HashSet<ThingDef>();

    foreach (var kvp in settings.categories)
    {
        if (onlyCategory != null && kvp.Key != onlyCategory)
            continue;

        // 原逻辑...
        foreach (var targetDef in GetTargetDefs(info))
        {
            if (onlyTargetDefName != null &&
                targetDef.defName != onlyTargetDefName)
                continue;

            // 计算 finalList、判断 changed。changed 出口共 4 处，统一收 ChangedTargets：
            //   ① 原版 comp 清空（声明为空且原本有链接）
            //   ② 自建 comp 整体移除（声明为空；无条件计——空列表自建 comp 也移除）
            //   ③ 新建 comp（原无 comp 且 finalList 非空）
            //   ④ 写入 finalList（内容有变化）
            // 每处出口同步 result.Applied++
        }
    }

    // 重建受影响设施的反向索引
    foreach (var facilityDef in affectedFacilities)
        facilityDef.GetCompProperties<CompProperties_Facility>()?
            .ResolveReferences(facilityDef);

    return result;
}
```

旧 `int ApplyInjection(settings)` 签名的调用者共 3 处（`Apply()` 启动注入 + 两个 UI `ApplyAndSave`），随本阶段全部迁移到新签名后**不保留旧入口转发**——无调用者的公共 API 是维护负担。

### 4.3 反向索引只重建“实际增删”的设施

当前代码把“旧列表∪新列表”的所有设施都加入 `affectedFacilities`。
例如目标原本连了 50 个设施，只断开 1 个时，会重建 50 个设施的反向索引。

改为只加入对称差集：

```csharp
if (oldList != null)
    foreach (var f in oldList)
        if (!finalList.Contains(f))
            affectedFacilities.Add(f);

foreach (var f in finalList)
    if (oldList == null || !oldList.Contains(f))
        affectedFacilities.Add(f);
```

更稳妥可用 `HashSet<ThingDef>` 比较：

```csharp
static void AddAffectedByDiff(
    HashSet<ThingDef> output,
    List<ThingDef>? oldList,
    List<ThingDef> newList)
{
    var oldSet = oldList == null
        ? new HashSet<ThingDef>()
        : new HashSet<ThingDef>(oldList);

    foreach (var f in newList)
        if (!oldSet.Contains(f))
            output.Add(f);

    var newSet = new HashSet<ThingDef>(newList);
    if (oldList != null)
        foreach (var f in oldList)
            if (!newSet.Contains(f))
                output.Add(f);
}
```

这样单击一条链接通常只重建 1\~2 个设施的反向索引，而不是几十个。

### 实施要求

1. **`ResolveReferences`** **单次成本 = O(全 Defs)**（原版引擎 virtual，override 内部全量扫 `AllDefsListForReading` 重建 `linkableBuildings`）。对称差把受影响设施缩到“实际增删”集合（断 1 条链 → 1\~2 个）：有配置启动总成本 ≈ 受影响设施数 × O(全 Defs)，按此量级设预期；UI 单击场景 1\~2 次可接受。
2. **对称差 old 基准 = 运行时 def 现值**：现状实现 `oldList = comp?.linkableFacilities` 已直接读 def 现值（2026-09-09 调研确认），保持该行不动即满足本要求。二次注入（启动注入后 UI 局部注入）时 def 现值已含首次注入结果，以此作基准保证与一次全量注入的结果一致。

### 4.4 `FacilityListEquals` 改成 O(n)

当前：

```csharp
foreach (var f in oldList)
    if (!newList.Contains(f))
        return false;
```

这是 O(n²)。改为先建一次 HashSet：

````csharp
private static bool FacilityListEquals(
    List<ThingDef>? oldList,
    List<ThingDef> newList)
{
    if (oldList == null || oldList.Count != newList.Count)
        return false;

    if (oldList.Count == 0)
        return true;

    var set = new HashSet<ThingDef>(newList);
    foreach (var f in oldList)
        if (!set.Contains(f))
            return false;

    return true;
}

### 实现说明

- `FacilityListEquals` 用 HashSet 比较，丢失**顺序与重复**语义；对 `linkableFacilities` 安全，因为引擎 `PotentialThingsToLinkTo` 按距离排序、不依赖列表序。在实现注释中钉死此前提。

### 实现说明（2026-09-09 调研核实，P4+P5 捆绑实施依据）

1. **一个目标 def 只归属一个类别**（Scanner 的已知类 thingClass 匹配与 Building 连通分量均为单归属划分）：`onlyCategory` 注入时 ChangedTargets 必在限定类别内。跨类别共享的只有设施 def，其反向索引经 `ResolveReferences` 全量反算（引擎按全 defs 现值重建 `linkableBuildings`）天然覆盖其他类别现状——§7.3 要求 3（跨类别共享设施）有结构性保证，无需额外交互。
2. **类别级 `allFacilityDefs` 不因 `onlyTargetDefName` 而跳过**：finalList = 类别全部设施 ∩ ShouldLink，目标过滤后仍需完整类别设施集；目标过滤只放在内层目标循环头部。
3. **changed 出口 4 处已逐一核实**（见 4.2 骨架注释），其中 ②（自建 comp 整体移除）无条件计数——孤儿清理按 ChangedTargets 过滤后靠它命中存量实例。

## 5. Phase 5：UI 只重连真正发生变化的目标

### 方案

`RelinkSpawnedThings` 增加按目标 Def 过滤的重载：

```csharp
public static int RelinkSpawnedThings(IEnumerable<ThingDef> changedTargets)
{
    if (Current.Game == null)
        return 0;

    var targetSet = new HashSet<ThingDef>(changedTargets);
    if (targetSet.Count == 0)
        return 0;

    int relinked = 0;

    foreach (var map in Find.Maps)
    {
        foreach (var targetDef in targetSet)
        {
            foreach (var thing in map.listerThings.ThingsOfDef(targetDef))
            {
                var comp = thing.TryGetComp<CompAffectedByFacilities>();
                if (comp == null)
                    continue;

                // 原有“孤儿 comp 清理/Notify_ThingChanged”逻辑
            }
        }
    }

    return relinked;
}
````

`map.listerThings.ThingsOfDef(targetDef)` 已确认存在（public，O(1) 字典返回），直接用；仅当未来版本 API 变动时再退回全图 `AllThings` 并按 `targetDef.defName` 过滤。

### UI 调用

`Dialog_FacilityMatrix.ApplyAndSave` 改为带范围：

```csharp
private void ApplyAndSave(
    string? onlyCategory = null,
    string? onlyTarget = null)
{
    var result = FacilityPatcher.ApplyInjection(
        settings, onlyCategory, onlyTarget);

    FacilityPatcher.RelinkSpawnedThings(result.ChangedTargets);
    settings.Write();
}
```

各入口：

| 操作                                  | 建议作用域               |
| ----------------------------------- | ------------------- |
| 单击切换一条连接                            | 当前类别 + 当前目标 defName |
| 退出批量模式                              | 当前类别                |
| 重置单个设施                              | 当前类别                |
| 重置单个主设施                             | 当前类别 + 该主设施         |
| 复制/粘贴到单个设施                          | 当前类别                |
| 复制/粘贴到单个主设施                         | 当前类别 + 该主设施         |
| “全部启用/禁用”且选主设施                      | 当前类别 + 该主设施         |
| “全部启用/禁用”且选设施                       | 当前类别                |
| 应用/导入预设（Dialog\_PresetManager 两处调用） | 全量（一次性操作，可接受）       |

### 实施要求（正确性）

1. **用** **`map.listerThings.ThingsOfDef(def)`** **取实例**（public，O(1) 字典返回），不要用全图 `AllThings` 遍历。
2. **`ChangedTargets`** **收集覆盖全部 changed 出口**：在判定 changed 的**每个出口**（含“自建 comp 整体移除”分支）统一 `result.ChangedTargets.Add(targetDef)`——孤儿清理分支按 ChangedTargets 过滤后，才能命中这类目标的地图存量实例（先逐个 `CompFacility.Notify_LinkRemoved` 解旧登记、清 `LinkedFacilitiesListForReading`、再移除实例 comp）。
3. **只重连目标 def 实例即可闭环**：目标实例 `Notify_ThingChanged → RelinkAll` 经 `Notify_NewLink / Notify_LinkRemoved` 反向修正设施实例登记。**跨类别共享设施**（设施 F 同时可连类别 A、B 的目标，仅注入 A）须专门回归：验证 F 的放置指示（读 `linkableBuildings`）与实例登记正确。
4. **无参** **`RelinkSpawnedThings()`** **不保留**（2026-09-09 调研确定）：预设管理器两处调用走全量注入 + `result.ChangedTargets` 重连（未变目标无需重连），无参全图 `AllThings` 扫描版无存在必要。UI 现有 7 处 `ApplyAndSave` 调用点（Dialog\_FacilityMatrix 5 处 + Dialog\_PresetManager 2 处）全部迁移到带范围版本。

## 6. Phase 6：`ShouldLink` 的 HashSet 缓存

### 问题

`ShouldLink` 使用 `List.Contains`，配置窗口每帧对可见格子调用，白名单大时线性查找累积明显。

### 方案

保留 `linkedTargets` 的 `List` 作为序列化格式，同时维护内存 HashSet 缓存。

在 `Settings` 内：

```csharp
private Dictionary<string, HashSet<string>> linkedSetCache = new();
```

```csharp
public bool ShouldLink(
    string category,
    string facilityDefName,
    string targetDefName)
{
    var key = MakeKey(category, facilityDefName);

    if (linkedTargets.TryGetValue(key, out var linked))
        return GetLinkedSet(key).Contains(targetDefName);

    return originalLinks.TryGetValue(key, out var orig)
        && orig.Contains(targetDefName);
}

private HashSet<string> GetLinkedSet(string key)
{
    if (linkedSetCache.TryGetValue(key, out var set))
        return set;

    set = new HashSet<string>(linkedTargets[key]);
    linkedSetCache[key] = set;
    return set;
}

private void InvalidateLinkedSet(string key)
    => linkedSetCache.Remove(key);
```

所有修改 `linkedTargets` 的地方都调用 `InvalidateLinkedSet(key)`：

- `ToggleLink`
- `SetLink` 最终经由 `ToggleLink` 或直接赋值时
- `EnableAllTargets`
- `DisableAllTargets`
- `SetLinkedList`
- `ResetToOriginal`：清空整个缓存
- `ResetFacilityToOriginal`：移除对应缓存
- `ResetTargetToOriginal`：移除对应缓存
- `SetTargetLinkedList` / `EnableAllTargets`（含“类别失效写空列表”分支）/ `DisableAllTargets` / `SetLinkedList`：按 key 失效
- `ExposeData`：须区分读写分支——**读档分支后清空整个缓存**；写档分支不清（启动 `FacilityPatcher.Apply` 内 `settings.Write()` 也会触发 ExposeData，若写档即清缓存将导致启动注入期间反复重建）

如果 `originalLinks` 某些 key 的 List 很长，也可以做同样的惰性 HashSet，但建议先只给用户可变的 `linkedTargets` 加，避免提高常驻内存。

## 7. Phase 7：增加可量化验证

> **阶段定位（2026-09-09 修订）：本阶段应提前为 Phase 0 执行**——先量化现状（启动扫描/注入 ms、单次 UI 单击 ms）再逐阶段优化，每阶段完成后复测对比。

### 7.1 启动计时/内存埋点

埋点挂在现有 FCDebug 门控上（Source/Utils/Debug/FCDebug.cs，发布态置 `DebugBuild = false` 即全短路。

计时统一用 `FCDebug.TimeScope("标签")` 作用域（using 包裹，Dispose 输出毫秒耗时）。
**注意门控是编译期** **`DebugBuild`** **而非运行时** **`EnableLog`**：启动计时发生在主菜单出现前，
用户无法打开菜单开关，挂 `EnableLog` 会丢失全部启动数据；`DebugBuild = false` 时返回空单例，零开销：

```csharp
using (FCDebug.TimeScope("启动·声明式注入 ApplyInjection"))
{
    // ScanAll / ApplyInjection ...
}
```

### 7.2 回归验证

优化后需要验证：

1. 无配置启动：所有目标 `linkableFacilities` 与 XML 原始状态一致；
2. 有配置启动：配置被正确重建；
3. 运行时单击连接/断开：仅对应目标被重连，且已放置建筑即时生效；
4. 重置/导入预设：语义不变；
5. 卸载某 Mod 后重启：缓存清空、缺失 defName 被静默跳过；
6. 同一进程内重复触发 `ScanAll`（如果未来加“重新扫描”）时结果正确。

### 7.3 补充回归清单

在 7.2 之外，逐阶段必须额外验证：

1. **二次注入不漂移**（§4.3 要求 2）：启动有配置注入后，UI 内再局部注入同一类别/目标，反向索引结果与“一次全量注入”完全一致；
2. **孤儿实例可清理**（§5 要求 2）：对“已整体移除自建 comp”的目标，局部注入后其地图上存量实例被正确解链并移除实例 comp；
3. **跨类别共享设施**（§5 要求 3）：仅注入类别 A 时，同连 A/B 两类的设施 F 的放置指示（`linkableBuildings`）与实例登记正确。

### 7.4 实施顺序

P7/Phase 0（先测量）→ P1 → P2 → P3（启动路径，独立可回归）→ **P4 + P5 捆绑**（UI 路径，互为前置，捆绑实施避免中间态不可用）→ P6（微优化，最后）。

## 8. Phase 8：预设窗口导出折叠与布局加固（UI）

> **阶段定位（2026-09-10 新增）**：P1–P7 均为启动/运行时性能优化；本阶段是与性能链路解耦的 UI 修复与交互精简，可独立实施、独立回归。动因来自实际使用观察——导出场景绝大多数是**全量导出**，细分来源属低频操作，现状却让它们常驻平铺、挤压版面。

### 问题

现状 `Dialog_PresetManager`（Source/UI/Dialog_PresetManager.cs）的 `DoWindowContents` 把“全部来源 + 每个 Mod 来源”按钮常驻平铺：

1. **版面被平铺按钮占用**：高频的全量导出与低频的细分多选地位相同，干扰识别、增加误操作；
2. **来源 wrap 行数无上限**：来源按钮按行换行，导出区高度随 Mod 数量线性增长；
3. **导入区被压缩甚至挤出**：导入区高度按“窗口底部固定预留（全局工具）− 当前 y”的剩余空间计算；当来源按钮约 9 行以上时，导出区高度逼近或超过该剩余空间，导入列表高度趋 0/负、全局工具被推出窗口——即用户实测到的“导入连接页面被压缩”。

### 方案

保持导出语义不变：折叠行左侧为**全部来源状态钮**（点击仅切换范围、不执行导出），真正执行导出的仍是行尾独立“导出”按钮；默认折叠，来源细分按钮仅展开后出现，并放入**限高滚动区**。该滚动区同时将导出区高度变为有界值，从根上消除问题 2/3。

#### 8.1 折叠 / 展开两态

新增窗口实例状态字段：

```csharp
/// <summary>来源细分区是否展开（默认折叠，聚焦全量导出）</summary>
private bool sourceExpanded;
```

**折叠态（默认）**，位于文件名行上方，仅一行：

- `[全部来源]` 状态钮：`allSelected == true` 时高亮（复用现状 `SelectAllSources` / `allSelected` 语义）；若当前已选部分来源（`allSelected == false`），文案随状态显示 `已选 {0} 个来源`，保证折叠后用户仍能看清导出范围，且可直接点击一键回全量；
- `[展开 ▸]` 按钮：置 `sourceExpanded = true`。

**展开态**：

- 首行：`[全部来源]` 状态钮 + `[收起 ▾]` 按钮（置 `sourceExpanded = false`）；两者都位于滚动区之外，点击可立即 `return`；
- 其下为来源按钮滚动视图，高度固定为 `SourceAreaH ≈ SourceBtnH * 5 + RowGap * 2`，超出部分滚动——Mod 数量再多也不撑高导出区；
- 各 Mod 来源按钮的单选/多选切换逻辑（`ToggleSource` / `ChosenSources`）与现有一致。

#### 8.2 布局约束

- 折叠态：导出区高度恒等于（来源行 1 行 + 文件名行 + 预览行），不再随 Mod 数量变化；
- 展开态：导出区在折叠高度上追加固定值 `SourceAreaH`，仍为有界值；
- 导入区维持现有“剩余空间分配”，此时导出区上限已知，导入区不再被压没，全局工具行位置恢复稳定；
- 滚动区高度 / 滚动条宽度沿用现有布局常量（`ScrollBarW`、`RowGap` 等），不新增魔法数字。

#### 8.3 滚动区内点击不得提前 `return`

来源按钮移入 `BeginScrollView` 后，点击分支若直接 `return`（现状代码如此），会跳过 `EndScrollView`，触发引擎 “Mouse position stack is not empty” 报错。按导入列表既有模式（`DrawImportList`），点击动作延迟到 `EndScrollView` 之后执行：

```csharp
Action? pendingSourceAction = null;
Widgets.BeginScrollView(sourceAreaRect, ref sourceScroll, sourceContentRect);
foreach (var source in allSources)
{
    // 仅收集动作，不在滚动区内 return
    if (Widgets.ButtonText(new Rect(...), source))
        pendingSourceAction = () => ToggleSource(source);
}
Widgets.EndScrollView();
pendingSourceAction?.Invoke();
```

折叠态无滚动，可保留立即 `return` 的旧写法；两态各占一个绘制分支。

### 实施要求

1. 仅修改 `Source/UI/Dialog_PresetManager.cs` 的导出区绘制并新增状态字段；`FacilityPreset` / `Settings` / `ChosenSources` / `DoExport` 语义不动；
2. 来源按钮区（折叠 1 行 / 展开 1 行 + 滚动区）始终绘制在文件名行之前的同一纵向顺序；
3. 新增翻译键：`FC.ExportExpand`（展开 ▸）、`FC.ExportCollapse`（收起 ▾）、`FC.ExportPartialFmt`（`已选 {0} 个来源`，折叠态文案）；
4. 展开/折叠为会话级 UI 状态，不落盘、不加配置项；
5. 位于滚动区内的任何按钮（含将来的收起钮若移入区内的变体）点击一律延迟执行，禁止提前 `return`。

### 验收

1. 来源 Mod ≥ 10 个时窗口布局不再被撑开，导入列表与全局工具保持可见可用；
2. 折叠态点击独立“导出”= 全量导出，与现状行为一致；
3. 展开选择部分来源后折叠，状态钮显示“已选 n 个来源”；再次展开勾选状态不回退；
4. 展开态点击任意来源按钮无控制台报错（验证 Begin/EndScrollView 配对）。

## 9. 预期效果

| 阶段                 | 优化前                  | 优化后                          |
| ------------------ | -------------------- | ---------------------------- |
| `ResolveType`      | 最坏 `O(K·q·N)`        | 每次扫描 `O(N)` 构建一次字典，之后 `O(1)` |
| 普通 Building 聚类     | 最坏 `O(B²·d)`         | `O(B·d + B)`                 |
| 无配置启动              | 全量类别矩阵重建             | 跳过注入                         |
| 单击一次链接             | 全类别重建 + 全图扫描         | 单目标重建 + 单目标类型重连              |
| 反向索引重建             | 旧∪新全部设施              | 只重建增删设施                      |
| `ShouldLink` UI 查询 | `List.Contains` O(n) | 用户覆盖表走 HashSet O(1)          |
| 预设窗口导出区（P8） | 来源按钮平铺，来源多时挤压导入/全局 | 折叠 + 来源限高滚动，导出区高度有界 |

整体期望是：

- 无配置启动：从“全量扫描 + 全量注入”降到“一次全 Def 扫描 + 建索引 + 分类”，最坏增长从接近二次压到接近线性；
- 有配置启动 / UI 操作：从“全量类目矩阵”变为“按变更目标/类别局部重建”；
- 预设窗口（P8）：全量导出默认零额外点击，来源细分在展开后的限高滚动区中选择，窗口在任何 Mod 数量下不被撑开。

P1–P7 不改变 RimFacilityCompat 的现有用户可见行为，也不会引入存档格式不兼容；Phase 8 仅改变预设窗口的默认布局（默认折叠、展开才显示细分来源），导出与连接语义不变。
