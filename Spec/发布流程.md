# RimFacilityCompat 发布流程

> 适用范围：GitHub Release 与 Steam 创意工坊的双渠道分发。
> 核心约束：**Debug 包与 Release 包必须在同一个 commit 上产出**，否则调试包失去作为排查基准的意义。

---

## 一、版本号约定

| 项 | 说明 |
|---|---|
| 唯一人工编辑点 | [About.xml](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/About/About.xml) 的 `<modVersion>` |
| 版本格式 | 语义化版本 `主.次.修订`（如 `1.0.0`）|
| Git tag | `v` + 版本号（如 `v1.0.0`），由打包脚本读取版本号后使用 |
| 预设文件格式版本 | [FacilityPreset.cs](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/1.6/Source/Data/FacilityPreset.cs#L46) 写入预设文件的 `Version="2"`，是导入时的结构兼容判断，属于**文件格式版本**，与发布版本无关，不要混用 |

发布时只需人工改一处 `<modVersion>`，其余（zip 命名、Release 标题、tag）全部由打包脚本从它派生。

## 二、两类产物

| 产物 | 编译配置 | `DebugBuild` | 包内 `<modVersion>` | 去向 |
|---|---|---|---|---|
| Release 包 | `Release` | `false` | `1.0.0` | Steam 创意工坊 + GitHub Release |
| Debug 包 | `Debug` | `true` | `1.0.0-debug` | 仅 GitHub Release（供作者/协作者定位问题）|

- `DebugBuild` 由 [FCDebug.cs](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/1.6/Source/Utils/Debug/FCDebug.cs#L18-L22) 的 `#if DEBUG` 决定，因此两个包是同一份源码的**两种编译结果**，不是两套代码。
- Debug 包在打包时会把包内 `<modVersion>` 改写为 `1.0.0-debug`。原因：zip 名带后缀只是一半，玩家在游戏内 mod 列表看到的版本号也必须可区分，否则收到反馈时无法判断对方装的是哪个包。仓库内的 `About.xml` 不会被改动。

## 三、发布包目录结构

zip 内顶层为 `RimFacilityCompat` 文件夹，解压后可直接放入 `Mods/`：

```
RimFacilityCompat/
├── About/                 # 含 PublishedFileId.txt，上传创意工坊必须保留
├── 1.6/
│   └── Assemblies/
│       └── FacilityCompat.dll
├── Languages/
└── Presets/               # 代码按 content.RootDir + "Presets" 读取，必须包含
```

**不进入发布包**：`1.6/Source/`（源码）、`1.6/Logs/`、`1.6/AssembliesDebug/`、`Spec/`（设计文档）、`dist/`（打包产物）。

## 四、编译输出隔离

[FacilityCompat.csproj](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/1.6/Source/FacilityCompat.csproj#L7-L10) 已按配置分流输出目录：

| 编译配置 | 输出目录 | 是否入库 |
|---|---|---|
| `Release` | `1.6/Assemblies/` | 是（保证 clone 即玩 + 创意工坊上传源）|
| `Debug` | `1.6/AssembliesDebug/` | 否（[.gitignore](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/.gitignore) 已忽略）|

这一步的意义：本地调试 F5 产生的 dll 永不覆盖仓库内已入库的发行版 dll，从根本上杜绝“忘记补编 Release，就把调试版传上工坊”。**不要依赖“先编 Debug 再编 Release”的先后顺序来保证正确性**，那是脆弱的。

## 五、打包

```powershell
powershell -ExecutionPolicy Bypass -File Tools\Build-Release.ps1
```

脚本 [Build-Release.ps1](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Tools/Build-Release.ps1) 依次完成：

1. 从 `About.xml` 读取版本号，并校验工作区是否干净、tag 是否已存在；
2. 分别以 `Release` / `Debug` 配置编译；
3. 按白名单组装 `dist/stage/release/` 与 `dist/stage/debug/`；
4. 压缩产出两个 zip（`dist/` 已被 git 忽略）。

产出：

```
dist/
├── RimFacilityCompat-1.0.0.zip
├── RimFacilityCompat-1.0.0-debug.zip
└── stage/                     # 组装中间目录，便于核对包内结构
```

## 六、GitHub 发布

GitHub Release 需要**两个 zip 资产**，不要只传 Debug 包（若 GitHub 也是你的分发渠道，玩家同样需要发行包）。

本机当前**未安装 `gh` CLI**。两种方式：

- **手动**：在 GitHub 仓库 → Releases → Draft a new release，tag 填 `v1.0.0`，把两个 zip 拖入资产区。
- **自动**：安装并登录 `gh` 后，执行

```powershell
powershell -ExecutionPolicy Bypass -File Tools\Build-Release.ps1 -CreateRelease
```

脚本会调用 `gh release create v<版本> <两个zip> --title v<版本> --generate-notes`；若未检测到 `gh` 则仅告警并跳过上传，zip 仍然产出。

## 七、Steam 创意工坊发布

创意工坊上传的是**整个 mod 文件夹**，不是 zip。上传源应为仓库目录本身（此时 `1.6/Assemblies/` 内即为 Release 版 dll）：

- 方式：游戏内开发者模式上传器 / RimPy / RimSort / SteamCMD；
- **`About/PublishedFileId.txt` 必须保留**，否则会新建工坊条目而不是更新现有页面；
- 只上传 Release 版，Debug 包不进工坊。

## 八、发布检查清单

- [ ] `About.xml` 的 `<modVersion>` 已更新并提交
- [ ] `git status` 干净（无未提交改动，确保两个包对应确定的 commit）
- [ ] 运行打包脚本，两个 zip 均产出
- [ ] 核对 `dist/stage/debug/.../About/About.xml` 内版本号为 `<版本>-debug`
- [ ] GitHub Release 上传 Release 包与 Debug 包
- [ ] 创意工坊上传 Release 目录，且 `PublishedFileId.txt` 仍在
- [ ] 更新 Release notes / 工坊更新说明

## 九、常见误区

1. **靠编译顺序保证 dll 正确**——已由输出目录隔离取代，不要再手动“补编 Release”。
2. **Debug 与 Release 之间改动代码**——会导致两个包不同源，Debug 包失去参照价值；应改成“一次产出两份”。
3. **只发 Debug 包到 GitHub**——玩家渠道同样需要发行包。
4. **把预设格式版本当发布版本**——两者独立演进，不要互相覆盖。
5. **打包时漏掉 `Presets/`**——作者预设会丢失，玩家需自行导入。
