# RimFacilityCompat 修复技术方案：单通道运行时声明式注入

> 文档版本：v1.0（2026-09-06）
> 状态：待评审 / 待实施
> 关联文档：[流程说明.md](流程说明.md)（描述当前旧架构，实施后需同步更新）

---

## 1. 背景

RimFacilityCompat 用于打通各 mod 的设施（`CompProperties_Facility`，如床头柜、梳妆台）与目标建筑（`CompProperties_AffectedByFacilities`，如床、工作台）之间的链接，实现跨 mod 兼容。

当前实现采用"生成 XPath 补丁文件（`FC_Generated.xml`）→ 重启生效"为主、可选 C# 运行时注入为辅的双通道架构。实测存在多个 bug，且整体链路笨重（三级 XPath fallback + 运行时兜底清理 + 双通道同步）。

本文档记录问题排查结论与修复技术方案。

## 2. 引擎机制验证（RimWorld 1.6 反编译源码）

以下结论是本方案的事实依据，均已通过 `e:\steam\steamapps\common\RimWorld\Source_Decompiled` 源码验证。

### 2.1 加载顺序：Patch 先于 XML 继承展开

[LoadedModManager.cs#L96-L153](file:///e:/steam/steamapps/common/RimWorld/Source_Decompiled/Assembly-CSharp/Verse/LoadedModManager.cs#L96-L153)：

```
LoadModXML()              读取所有 mod 的 XML
    │
CombineIntoUnifiedXML()   纯合并（无继承展开）
    │
ApplyPatches()            ← 应用所有 PatchOperation（此时继承尚未展开）
    │
ParseAndProcessXML()      XmlInheritance.TryRegister → XmlInheritance.Resolve（继承展开）
    │                     之后解析为 Def 对象
```

**含义**：XPath 补丁执行时，子类 def 的 XML 节点中**看不到**声明在 abstract 父类中的 comp。

### 2.2 蓝图 / 放置预览直接读建筑 def

蓝图 def 由 `ThingDefGenerator_Buildings` 动态生成，仅携带 `Forbiddable`/`Styleable` comp，不复制设施 comp。放置时的"将连接的设施"预览（`CompAffectedByFacilities.DrawPlaceMouseAttachmentsToPotentialThingsToLinkTo`）传入的是**建筑 def 本身**，内部调用 `myDef.GetCompProperties<CompProperties_AffectedByFacilities>()`。

**含义**：运行时直接修改建筑 def 的 comps 后，蓝图与放置预览**立即可见**。旧代码注释"运行时注入在蓝图阶段不可见"的担忧不成立。

### 2.3 CompProperties_AffectedByFacilities 结构极简

[CompProperties_AffectedByFacilities.cs](file:///e:/steam/steamapps/common/RimWorld/Source_Decompiled/Assembly-CSharp/RimWorld/CompProperties_AffectedByFacilities.cs) 仅含一个字段：

```csharp
public List<ThingDef> linkableFacilities;
```

**含义**：运行时新建 / 重建该 comp 实例零风险，无需 XML 反序列化参与。

### 2.4 linkableFacilities 重复条目的实际危害

[CompAffectedByFacilities.PotentialThingsToLinkTo（L357-L401）](file:///e:/steam/steamapps/common/RimWorld/Source_Decompiled/Assembly-CSharp/RimWorld/CompAffectedByFacilities.cs#L357-L401)：

```csharp
for (int i = 0; i < compProperties.linkableFacilities.Count; i++)
    enumerable = enumerable.Concat(myMap.listerThings.ThingsOfDef(compProperties.linkableFacilities[i]));
```

同一 def 在列表中出现 N 次，其 `ThingsOfDef` 结果被拼接 N 次，随后按 `maxSimultaneous` 配额返回：

- `maxSimultaneous = 1`（Core 大多数设施）：被 `alreadyReturnedCount` 挡住，无游戏性危害，仅性能浪费；
- `maxSimultaneous > 1`：**同一实例占用多份配额，该设施实际可同时连接数量减少**。

### 2.5 defs 的静态性与存档安全

- Def 数据在进程生命周期内静态存在，`ExecuteWhenFinished` 时机（主菜单出现前）修改 def 后，玩家进图 / 建造 / 读档全部使用新数据；
- `ThingDef.comps` 内容不写入存档，运行时重建不产生存档膨胀；
- 运行时注入**不落盘** → 下次启动 defs 自动回到 XML 原始状态（区别于 XPath patch：patch 每次启动都会在 XML 层重新注入一遍）。

### 2.6 已放置建筑的重连入口

`CompAffectedByFacilities.Notify_ThingChanged()` 为 public，内部触发 `RelinkAll()` → 重新扫描周边设施并重建链接。可在存档加载后调用，使旧建筑立即应用新配置。

## 3. Bug 清单（排查结论）

### 3.1 结构性 bug（XPath 生成路线的根因）

#### BUG-1：deep XPath 对继承型目标必然失败 → 产生重复 comp

[XpathGenerator.cs#L108](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/XpathGenerator.cs#L108) 的 deep 路径：

```
/Defs/ThingDef[defName="X"]/comps/li[@Class="CompProperties_AffectedByFacilities"]/linkableFacilities
```

只有当设施 comp **直接写在目标 def 自己的 XML** 中才能匹配。而 Core / 各大 mod 的床族（`BedBase`）、工作台族（`BenchBase`）等的 `CompProperties_AffectedByFacilities` 几乎都声明在 abstract 父类中。

由 §2.1，Patch 执行时继承未展开 → deep 匹配失败 → fallback（`BuildCompsMatch`）向子类 comps 追加**一个全新的完整 comp** → 继承展开后该 def 拥有 **2 个同类 comp** → 完全依赖 [CleanupComps](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/FacilityPatcher.cs#L112) 运行时合并兜底。

> 这是"三级 fallback + 兜底清理"互相打补丁的根源。对继承型目标，deep 分支实际永远失败，前两级 fallback 空转。

#### BUG-2：补丁 value 包含原始链接 → linkableFacilities 出现重复条目

首次运行流程：`ResetToOriginal()` 保留原始链接 → [XpathGenerator.cs#L65-L68](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/XpathGenerator.cs#L65-L68) 生成补丁时 `ShouldLink` 过滤后的列表**包含原始设施**，而 `PatchOperationAdd` 为纯追加语义 → 重启后：父类 XML 中一份 + patch 追加一份 = **重复条目**。

且 [CleanupComps 只处理"多个 comp 的合并"，从不清理单个 comp 内部的重复条目](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/FacilityPatcher.cs#L138-L150)。

危害见 §2.4。

#### BUG-3："排除原始链接"结构性无效

`PatchOperationAdd` 只增不减。用户在设置界面排除某条**原始就存在**的链接 → 保存 → 重启 → 该链接依然生效（它写死在目标 mod 的 XML 里）。默认配置（`enableRuntimePatch = false`）下此功能完全不起作用——实测"设置不生效"的直接原因。

#### BUG-4：originalLinks 扫描基准被上次补丁污染 → 配置漂移 / 丢失

`FC_Generated.xml` 存在时，本次启动 defs 在进入本 mod 代码前**已被 patch 修改**，而 [ScanOriginalLinks](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/FacilityPatcher.cs#L211) 在此后才扫描 → 注入结果被当作"原始状态"。连锁后果：

1. "全部重置"实际变成"回到上次补丁状态"，永远回不到真原始；
2. 普通 Building 连通分量分组（[FacilityScanner.cs#L195](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/FacilityScanner.cs#L195)）基于 `linkableFacilities` 计算，被注入结果污染后组结构漂移 → 类别 key `Building:{anchor}` 变化 → `excludedTargets` 的 key（`"类别|设施"`）失配 → **用户配置静默丢失**；
3. [XpathGenerator 的 hasComp 判断](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/XpathGenerator.cs#L72) 基于污染 defs，deep/comps 分支每次重启摇摆。

#### BUG-5：fallback 目标构建会把所有普通 Building 当目标

[XpathGenerator.cs#L48-L52](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/XpathGenerator.cs#L48-L52)：

```csharp
targetDefNames = DefDatabase<ThingDef>.AllDefs
    .Where(def => def.thingClass != null && def.thingClass.Name == thingClassName)
```

当 `thingClassName == "Building"`（普通 Building 组）且 `savedTargets` 为空时，墙、门等一切普通 Building 都会成为注入目标。

### 3.2 双通道互踩

#### BUG-6：runtimePatch 与 xpath 补丁双写不同步

- xpath patch 在 XML 层注入（`ShouldLink` 过滤）+ `PatchTarget` 在 def 层注入（同样过滤），两边各写一份 → xpath 注入产生的重复条目因 `ShouldLink = true` 不会被运行时移除，长期存留；
- 首次运行时序颠倒：[PatchTarget（excluded 为空 → 全量注入）先于 ResetToOriginal（excluded = 全部非原始）执行](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/FacilityPatcher.cs#L50-L87)，随后生成的补丁只含原始链接 → 开启 runtimePatch 的用户预期"开箱全兼容"落空。

### 3.3 次要问题

| 编号 | 问题 | 位置 |
|---|---|---|
| BUG-7 | `GetMode` 的 None 判定用 `excluded.Count >= targets.Count`，mod 卸载后残留条目使 count 虚高 → 误判 None | [Settings.cs#L92](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/Settings.cs#L92) |
| BUG-8 | `CalcHeight` 手动列表行高按 24f 计算，`CheckboxLabeled` 实际行高约 30f → 长列表底部被裁切 | [Mod.cs#L369](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/Mod.cs#L369) |
| BUG-9 | `IsModified()` 恒返回 `true`（写死） | [Settings.cs#L232](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/Settings.cs#L232) |
| BUG-10 | `Building_Bed` 类别同族扩展（`IsAssignableFrom`）会把更具体的 `Building_CryptoBed` 也收入 targets → 同一目标跨类别重复出现 | [FacilityScanner.cs#L92-L99](file:///e:/steam/steamapps/common/RimWorld/Mods/RimFacilityCompat/Source/FacilityScanner.cs#L92-L99) |

### 3.4 体验问题

- 配置生效需"改配置 → 保存 → 重启"，首次运行甚至需要**两次重启 + 手动保存**；
- 保存后当前会话 defs 不变（runtimePatch 关闭时），用户进游戏发现"没反应"。

## 4. 修复技术方案：单通道运行时声明式注入

### 4.1 核心决策

**彻底移除"生成 XPath 补丁文件"通道，保留并做实运行时注入，且注入语义从"增量追加"改为"声明式重建"。**

可行性依据：§2.2（蓝图预览读 def，注入即时可见）、§2.3（comp 结构极简）、§2.5（defs 静态、不落盘、每次启动自动回到原始状态）。

**"重建"是关键**：每个目标的最终 `linkableFacilities` ≡ 配置声明的状态（类别下所有设施 ∩ 未被排除的集合）：

- 增、删皆可 → BUG-3 消失（原始链接也可排除）；
- 幂等 → 重复启动 N 次结果一致，无重复条目 → BUG-2 消失；
- 单 comp 唯一 → BUG-1 的重复 comp 来源消失；
- 不落盘 → 每次启动 defs 自动干净 → 扫描 / `originalLinks` / 连通分量分组天然无污染 → BUG-4 连根消失；
- 单通道 → BUG-6 消失。

### 4.2 新流程

```
游戏启动（LongEventHandler.ExecuteWhenFinished，主菜单出现前）
    │
    ▼
┌────────────────────────────────────────────────┐
│ 阶段一：扫描（干净 defs，未被任何注入修改）       │
│ FacilityScanner.ScanAll() → categories          │
│ ScanOriginalLinks()  → originalLinks（真原始）   │
└────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────┐
│ 阶段二：迁移清理                                 │
│ 若存在旧版遗留的 1.6/Patches/FC_Generated.xml    │
│ → 自动删除（防止 XML 层与运行时双通道叠加）       │
└────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────┐
│ 阶段三：声明式注入 ApplyInjection()              │
│ 对每个目标 def：                                 │
│   设施列表 = 类别下所有设施 ∩ ShouldLink(配置)    │
│   - 无 comp → 新建并添加到 def.comps             │
│   - 有 comp → 重建 linkableFacilities 为上述列表  │
└────────────────────────────────────────────────┘

设置界面操作（任意勾选 / 排除 / 重置 / 粘贴）
    │
    ▼
立即调 ApplyInjection() + Settings.Write()
    → 当次会话即时生效，无需重启
```

### 4.3 ApplyInjection 伪代码

```csharp
/// 对所有目标重建设施链接：目标最终状态 ≡ 配置声明状态
public static void ApplyInjection(FacilityCompatSettings settings)
{
    foreach (var (category, info) in settings.categories)
    {
        // 类别下全部设施 def（GetNamedSilentFail 过滤失效 defName）
        var allFacilityDefs = info.facilities.Values
            .SelectMany(x => x)
            .Distinct()
            .Select(fn => DefDatabase<ThingDef>.GetNamedSilentFail(fn))
            .Where(def => def != null)
            .ToList();

        foreach (var targetDef in GetTargetDefs(info))
        {
            // 该目标的最终链接 = 类别全部设施 - 被排除的
            var finalList = allFacilityDefs
                .Where(f => settings.ShouldLink(category, f.defName, targetDef.defName))
                .ToList();

            var comp = targetDef.comps
                .OfType<CompProperties_AffectedByFacilities>()
                .FirstOrDefault();

            if (finalList.Count == 0)
            {
                // 声明状态为空：移除自建 comp（保留原版 XML 自带 comp，仅清空列表亦可，
                // 实施时二选一并保持一致）
                if (comp != null && /* comp 为本 mod 运行时所建 */) { ... }
                continue;
            }

            if (comp == null)
            {
                comp = new CompProperties_AffectedByFacilities();
                targetDef.comps.Add(comp);
            }
            comp.linkableFacilities = finalList;   // 整体重建，非追加
        }
    }
}
```

> 实施注意：需区分"原版 XML 自带的 comp"与"本 mod 运行时新建的 comp"，避免声明状态为空时误删原版数据导致下次启动语义漂移。建议以 defName → 是否原版有 comp 的启动期快照（内存字典）记录。

### 4.5 数据兼容与迁移

| 项 | 处理 |
|---|---|
| `excludedTargets` | **结构保留不变**，老用户配置无缝迁移（`"类别|设施"` key 语义不变） |
| `savedCategories` / `savedFacilities` / `savedTargets` | 停止序列化；存档 XML 中的残留键会被 RimWorld 忽略，无需清理 |
| `enableRuntimePatch` | 停止序列化；行为恒等于旧版"开启" |
| 旧 `FC_Generated.xml` | 启动时自动删除 + 日志提示。即使残留，声明式重建也会覆盖 XML 层注入结果，最终状态一致，删除仅为消除 patch 报错噪音与启动膨胀 |
| 类别 key 稳定性 | 普通 Building 连通分量分组在干净 defs 上计算，每次启动结果一致；但**历史被污染会话中保存过的配置**若使用了漂移后的类别 key，无法自动找回——迁移期可在设置界面提示用户复核一次 |

### 4.6 明确不做的事

- 不做 XML 落盘的任何形式补丁（含 `PatchOperationReplace` 方案——虽然 Replace 可解决追加重复与移除问题，但仍绕不开"继承未展开 → 匹配不到父类 comp"的根本障碍，且仍需重启生效）；
- 不引入 Harmony 补丁（当前需求纯 def 数据操作，`ExecuteWhenFinished` + public API 足够）。

## 5. 风险与边界

| 风险 | 评估与对策 |
|---|---|
| 已放置建筑不自动重连 | def 重建不触发重连，旧建筑维持建造时的链接；新建筑用新配置。可选增强（§4.4 末行）用 `Notify_ThingChanged()` 解决 |
| `ExecuteWhenFinished` 时机 | 在主菜单出现前执行，玩家尚未进图；所有蓝图 / 建造 / 读档均在其后，时机安全 |
| mod 增删 | 每次启动重新扫描重建，自动适配；失效 defName 经 `GetNamedSilentFail` 过滤，不产生 null 引用 |
| 同类 mod 冲突 | 若其他 mod 也在运行时改写同一 def 的 comps，以加载顺序后者为准（与本 mod 内的双通道互踩是两回事，属正常 mod 冲突范畴） |
| 性能 | 重建为一次性启动开销（数百 def 的列表重建，毫秒级）；设置界面每次操作重跑全量 `ApplyInjection`，如出现卡顿可增量只跑受影响类别（预留优化点） |
| 首次运行默认语义 | 沿用现状：首次无配置 → `ResetToOriginal()` 语义（仅保留原始链接）。若希望"开箱全兼容"，改为默认 excluded 为空即可——**需产品决策，默认维持保守语义** |
